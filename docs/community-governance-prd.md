# Firefly 社区共识治理 PRD

版本：v1.0  
更新时间：2026-05-26

## 1. 背景

Firefly 的核心内容天然是 UGC。  
如果平台采用中心化人工审核，运营成本会迅速失控，且很容易把项目拖成一个需要长期值守的审核台。

因此，Firefly 的治理方向调整为：

- 平台不承担日常人工审核
- 平台不直接判定“真相”
- 平台负责规则、阈值、风控与异常升级
- 社区通过加权共识推动内容进入不同公开状态

一句话定义：

**Firefly 是一个社区验证驱动的地理情报看板，而不是一个人工审核驱动的内容平台。**

## 2. 产品目标

### 2.1 核心目标

1. 降低平台人工审核负担
2. 控制风险类内容的滥用成本
3. 提高爱心类信息的持续可用性
4. 让公开状态由“管理员判断”转为“社区共识判断”

### 2.2 成功标准

- 新提交内容不需要人工逐条审核
- 多数点位靠社区反馈自然流转状态
- 错误信息能够被社区快速打回或降级
- 长时间无人维护的信息能够自动衰减

## 3. 内容类型与治理差异

## 3.1 风险类内容

包括：

- 投毒点
- 虐待事件
- 捕兽夹
- 偷盗预警
- 失踪协查
- 可疑车辆

特点：

- 时效性强
- 风险高
- 容易被滥用或恶意构造

治理原则：

- 先弱曝光，再逐步放大
- 必须结构化提交
- 需要附近用户多次确认
- 自动过期与降级

## 3.2 爱心类内容

包括：

- 救助站
- 爱心粮仓
- 友好医院
- 救助人
- 诱捕协助者

特点：

- 重点不是“证据审判”，而是“持续可信”
- 更适合信用与声誉模型
- 需要长期维护

治理原则：

- 以社区可联系性和协作反馈为主
- 持续心跳而不是一次性审核
- 长期无人确认则自动降权

## 4. 状态机

每条点位采用统一状态机，但不同类型的阈值不同。

## 4.1 核心状态

### `pending`

- 刚提交
- 尚未形成社区共识
- 默认仅弱曝光

### `limited`

- 获得初步共识
- 可公开，但带“待验证”或“低可信”标签
- 排序权重较低

### `verified`

- 达到稳定共识
- 进入主图层正常展示
- 排序权重提升

### `disputed`

- 社区反馈冲突较大
- 被多名高可信用户打回
- 默认折叠、弱曝光或仅在详情页可见

### `expired`

- 长时间无新确认
- 自动降级
- 不删除记录，但默认不进入主图层

## 4.2 风险类状态流转

- 新提交 -> `pending`
- 达到初步确认阈值 -> `limited`
- 达到高可信阈值 -> `verified`
- 被集中质疑或过期 -> `disputed` / `expired`

## 4.3 爱心类状态流转

- 新提交 -> `limited`
- 获得多次有效合作反馈 -> `verified`
- 长时间无人确认 -> `expired`
- 多次无效反馈或失联反馈 -> `disputed`

## 5. 社区反馈动作

前台不做开放评论区，优先使用结构化反馈。

## 5.1 通用动作

每条点位都支持：

1. `confirm_valid`
   - 确认有效

2. `mark_doubtful`
   - 信息存疑

3. `mark_outdated`
   - 信息过期 / 已变化

## 5.2 风险类附加动作

1. `seen_similar`
   - 我也看到过类似情况

2. `not_found_on_site`
   - 现场未发现相关情况

## 5.3 爱心类附加动作

1. `contact_success`
   - 我联系过，信息有效

2. `service_completed`
   - 我接受过协助，信息可信

3. `contact_failed`
   - 联系失败 / 信息失效

## 6. 前端交互设计

## 6.1 地图页

每个点位除类别外，还显示可信状态：

- `pending`：灰色边框或低对比标签
- `limited`：普通点位 + “待验证”
- `verified`：正常主图层
- `disputed`：折叠展示或弱曝光
- `expired`：默认不进主图层，仅搜索或详情可见

详情卡内新增：

- 社区状态标签
- 当前可信度等级
- 最近更新时间
- 附近用户确认次数
- 快速反馈按钮

## 6.2 提交页

风险类表单新增：

- 发现时间
- 是否本人目击
- 是否有图片证据

爱心类表单新增：

- 服务类型
- 可用时段
- 联系方式公开策略

## 6.3 详情页反馈交互

详情页底部提供“结构化反馈”组件，而不是评论区。

形式建议：

- 一个“确认有效”主按钮
- 一个“信息存疑”次按钮
- 一个“信息过期”次按钮
- 根据类型补充专属动作

反馈后立即显示：

- 本次反馈已记录
- 当前状态变化提示
- 社区共识进度条或阶段文本

## 6.4 个人贡献页

用户应能看到自己的：

- 提交记录
- 反馈记录
- 被社区确认次数
- 当前信誉等级

这不是为了社交化，而是为了形成责任感和可见激励。

## 7. 用户信誉分规则

Firefly 不采用简单人数投票，而采用加权信誉。

## 7.1 初始原则

- 新用户或新设备信誉低
- 附近长期活跃、历史准确的用户权重更高
- 信誉分只影响反馈权重，不影响基本浏览能力

## 7.2 加分行为

### 提交类

- 提交的点位后来进入 `verified`
- 提交的点位在一定周期内未被打回

### 反馈类

- 确认有效的反馈后来被多数高可信用户支持
- 举报 / 存疑反馈后来被系统证实有效

### 活跃类

- 在同一城市或片区稳定活跃
- 长期没有异常行为

## 7.3 扣分行为

- 提交内容频繁进入 `disputed`
- 多次被社区判定为无效或恶意
- 高频重复提交
- 恶意举报
- 与大多数高可信反馈长期反向冲突

## 7.4 信誉层级建议

- `L0` 新用户
- `L1` 普通参与者
- `L2` 稳定贡献者
- `L3` 高可信本地协作者

前台不一定公开精确分数，但可以公开等级。

## 8. 邻近优先机制

Firefly 的审核共识必须是 LBS 优先。

反馈权重建议由三部分共同决定：

1. 用户信誉分
2. 用户与点位的地理邻近度
3. 用户与该类别的历史相关度

例如：

- 南山区的投毒点
- 最近 14 天内在南山区有活跃记录的用户反馈权重更高

这样能显著降低异地刷票和无关用户干预。

## 9. 时间衰减

## 9.1 风险类

- 默认有效期：7 到 30 天
- 超期后自动降到 `expired`
- 有新确认则续期

## 9.2 爱心类

- 默认心跳周期：90 到 180 天
- 长期无人确认则降级
- 若再次获得联系成功反馈，可恢复

## 10. 平台角色

平台不做日常人工审核员，只处理以下升级事件：

1. 法律投诉
2. 严重隐私泄露
3. 集中刷屏攻击
4. 大规模恶意操纵
5. 社区长期无法形成共识的异常点位

这意味着平台只处理异常治理，而不处理日常内容判定。

## 11. 风险控制策略

## 11.1 风险类文案降断言

前台展示不要采用断言式结论。

例如：

- 不写“此处确定投毒”
- 改写为“收到关于该区域的投毒风险情报”

## 11.2 隐私保护

- 爱心类点位继续默认模糊坐标
- 敏感联系方式继续默认不公开
- 风险类避免公开个人身份信息

## 11.3 反刷

- 单指纹频控
- 附近优先分发
- 新账号反馈权重受限
- 重复坐标与重复文本去重

## 12. MVP 建议

第一阶段不做复杂用户体系，也能先落这套机制。

建议 MVP 只实现：

1. 五状态模型：`pending / limited / verified / disputed / expired`
2. 三个通用反馈动作
3. 风险 / 爱心差异化阈值
4. 指纹级信誉基础版
5. 时间衰减
6. 结构化前台反馈入口
7. 异常点位的人工升级入口

## 13. 后续版本

### Phase 2

- 用户信誉等级展示
- 区域活跃协作者标识
- 贡献记录页

### Phase 3

- 更细的邻近权重模型
- 更成熟的争议解决策略
- 多城市治理看板

## 14. 结论

Firefly 的治理模型不应是“平台审核内容”，而应是“平台管理社区共识规则”。

这是这类项目唯一可持续的运营方式。
